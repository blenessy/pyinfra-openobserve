# AGENTS.md

## Project overview

`pyinfra-openobserve` is a pyinfra deploy package that installs and configures OpenObserve observability components on remote hosts. It ships two high-level deploy targets:

- `deploy_openobserve_agent` — installs the OpenTelemetry Collector contrib binary and configures it as a systemd service that ships logs, journald, and host metrics to an OpenObserve OTLP endpoint.
- `deploy_openobserve_server` — placeholder for OpenObserve Server installation (currently unimplemented).

It is consumed as a local pyinfra plugin (via `uv run --directory example -- pyinfra ...`) and is inspired by `pyinfra-prometheus`.

## Repository layout

- `src/pyinfra_openobserve/` — the deploy package
  - `__init__.py` — public `deploy_openobserve_agent` entry point
  - `agent.py` — `install_openobserve_agent` and `configure_openobserve_agent` low-level deploy functions
  - `server.py` — reserved for the server deploy (empty for now)
  - `defaults.py` — `DEFAULTS` dict applied as pyinfra `data_defaults` (versions, user, home, SHA256 sums)
  - `templates/` — default `otel-config.yaml` and `otel-collector.service` Jinja2 templates
- `example/` — runnable example deploy that demonstrates overriding templates and inventory
  - `example/inventory.py` is gitignored and holds real-looking credentials locally; never commit it
  - `example/templates/` — user-supplied template overrides loaded via `primary_templates_path`
  - `example/group_data/all.py` — group data overrides
- `pyproject.toml` — project metadata, Ruff, and ty configuration
- `uv.lock` — locked dependency versions
- `README.md` — usage and deploy argument reference

## Development environment

- Python version: `3.14` as specified by `.python-version`
- Dependency and command runner: `uv`
- Do not install dependencies globally; use the project environment managed by `uv`.

Initialize or synchronize the environment with:

```sh
uv sync
```

pyinfra itself is a dev dependency (`pyinfra>=3.9,<4.0`); the runtime package has no pinned dependencies because it is loaded as a plugin by an existing pyinfra project.

## Quality checks

Before submitting changes, run:

```sh
uv run ruff check
uv run ruff format
uv run ty check
```

Ruff is configured with a 120-character line length and `select = ["ALL"]`, with targeted ignores documented inline in `pyproject.toml` (e.g. `PTH` is intentionally ignored because the codebase deliberately uses `os.path`). Prefer fixing the underlying issue rather than adding a new ignore. The `example/` directory is excluded from Ruff.

There is no test suite in the repository. If adding behavior, add focused tests under a `tests/` directory and document how to run them.

## Coding conventions

- Follow modern Python typing and the existing Ruff configuration.
- Keep deploy code under `src/pyinfra_openobserve/`.
- Preserve the existing split between high-level `@deploy` entry points in `__init__.py` and low-level operations in `agent.py` / `server.py`.
- Use `os.path` consistently with the rest of the codebase (do not switch to `pathlib` gratuitously; `PTH` is intentionally ignored).
- Keep functions small and named descriptively; add docstrings for public deploy functions and helpers.
- pyinfra deploy functions must use the `@deploy` decorator and accept host data via `host.data`. Do not introduce module-level mutable state.
- When adding new `host.data` keys, declare their defaults in `defaults.py` so they are visible and overridable via inventory/group data.

## Templates and overrides

- Default templates live in `src/pyinfra_openobserve/templates/`.
- Users override templates by passing `primary_templates_path` to `deploy_openobserve_agent`. `find_template()` prioritizes that path and falls back to the default. Preserve this fallback behavior.
- Templates are rendered by pyinfra's `files.template`. They receive explicit kwargs (`o2_otel_url`, `o2_otel_auth_header`, `o2_agent_home`, `o2_agent_user`) plus `host_data=host.data` so templates can reference any host data field. Keep this contract when adding new template variables.

## Deploy behavior and constraints

- `install_openobserve_agent` downloads the `otelcol-contrib` release tarball, verifies its SHA256 against `o2_agent_otelcol_sha256sums` for the host's OS/arch (raising `DeployError` on mismatch), extracts it, and symlinks the binary into `~o2_agent_home/bin/otelcol-contrib`.
- `configure_openobserve_agent` renders `otel-config.yaml` and `otel-collector.service`, then ensures the `otel-collector` systemd service is running and enabled, restarting it only when the rendered files changed (`_if=lambda: otel_config.did_change() or service_config.did_change()`). Preserve this conditional restart behavior.
- The OTel `Authorization` header is a Base64-encoded `Basic <user:pass>` token generated by `otel_auth_header()`. Never log this header, the username, or the password.
- Defaults target Ubuntu/Debian-style systems (e.g. `o2_agent_groups` includes `systemd-journal`). Note this assumption when changing user/group logic.

## Configuration and secrets

- Never commit plaintext API keys, passwords, OTLP tokens, or `Authorization` header values.
- `example/inventory.py` is gitignored precisely because it holds credentials. Do not commit it, do not commit replacement inventory files that contain real secrets, and do not print their contents in logs or agent output.
- When documenting inventory files in examples or docs, use placeholder values (e.g. `o2oi_**********************`) as `example/README.md` already does.
- Do not modify production or shared deployment credentials without explicit authorization.

## Running the example

The example is the canonical way to exercise the package locally. From the repository root:

```sh
uv run --directory example -- pyinfra inventory.py deploy.py -y
```

`example/inventory.py` must be created locally (it is gitignored); see `example/README.md` for the expected shape. The example passes `primary_templates_path` pointing at `example/templates/`, so user overrides there take precedence over the bundled templates.

## Dependency changes

- Update dependencies in `pyproject.toml`.
- Regenerate and commit `uv.lock` with:

```sh
uv lock
```

- Keep `pyinfra` pinned within the supported major version (`>=3.9,<4.0`) unless there is a deliberate reason to widen it.
- Runtime dependencies should remain empty or minimal; this package is a plugin loaded into an existing pyinfra project.

## Documentation

Update `README.md` when changing:

- the public deploy function signatures or arguments
- default values in `defaults.py`
- template override behavior or the `primary_templates_path` contract
- example run commands or inventory shape

Keep the `NOTICE` attribution to `pyinfra-prometheus` intact.

## Change checklist

Before finishing:

1. Run `uv run ruff check` and `uv run ruff format`.
2. Run `uv run ty check`.
3. Add or update tests for behavioral changes when practical.
4. Review the diff for accidental secrets, real credentials, or committed `inventory.py` files.
5. If defaults (versions, SHA256 sums, user/home) changed, verify they match an upstream `otelcol-contrib` release and update both `defaults.py` and `README.md`.
6. Update relevant documentation.
7. Report any checks that could not be run and why.
